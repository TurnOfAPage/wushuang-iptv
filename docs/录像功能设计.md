# 录像功能（本地 DVR）技术设计

> 状态：**P1+P2 已实现**（2026-11-23，独立产品「无双IPTV录像工具」v1.0.0，`recorder/` 目录）
> 实现记录见文末 §16；产品文档：recorder/README.md · CLI使用说明.md · 使用说明.md
> 目标版本：主工具不变（v2.2.1）；录像产品独立版本 `recorder/recinfo.py`（v1.0.0）
> 决策记录：2026-11-22 与作者讨论确定——
> ① 用户呼声最高的「回看」需求，**不做运营商真回看**（单播鉴权/克隆机顶盒 option60 路线，逐省适配成本高、隐私与合规风险大，整体搁置）；
> ② 改做**自定义录像**：把已经免鉴权收到的组播直播流录下来，事后局域网点播；
> ③ 主场景为 **NAS/软路由 7×24 常开**；
> ④ **CLI 与 GUI 同步设计、同步落地**（核心模块共用，改一处两边生效）；
> ⑤ 2026-11-23 作者追加决策：**独立发行**——很多人不需要录像，做成单独产品（独立 exe/版本号），主工具零改动。

## 1. 背景与原理边界

现有工具的全部能力建立在「直播 = 组播，免鉴权」之上（见 `src/main.py` HELP_TEXT）：
任何设备进入 ITV VLAN 加组即可收流，`verify.py` 加组解析、`proxy.py` 组转单均不需要账号。

录像的本质是这条能力的自然延伸：

```
能收流（verify 已证明） → 能转发（proxy 已证明） → 能存盘（本设计） → 能点播（proxy 扩展）
```

**与真回看的本质差距（宣传文案必须说清）**：只能录「开始录制之后」的内容，不能回溯过去。
常开设备 + 预约录像可覆盖「错过直播补看」这一最大诉求；P3 滚动时移可再补「最近 N 分钟」。

## 2. 目标 / 非目标

**目标**
- 手动即时录制任意已验证频道，输出标准 MPEG-TS 文件；
- 预约录制（手动指定时间段，或按公共 XMLTV 节目单点选）；
- 录制计划持久化，进程/设备重启后可恢复；
- 转发服务内建录像点播（HTTP Range 拖动）与录像播放列表；
- 磁盘配额与自动清理；
- CLI（headless NAS）与 GUI（Windows 桌面）功能对等；
- 核心零第三方依赖、不需要管理员/root（与 verify/proxy 同级）。

**非目标**
- 运营商回看/时移源抓取、机顶盒鉴权克隆（已决策搁置）；
- MP4 转封装/转码（需要 ffmpeg 或手写 remux，违背零依赖；TS 直录 + P3 HLS 兜底）；
- 公网访问（沿用「仅限局域网」红线；`wan/` 鉴权转发本期不改动）；
- 运营商 EPG 接入（需鉴权，用公共 XMLTV 替代）。

## 3. 总体架构

```
公共 XMLTV（用户主动更新，同 refdb update 模式）
        │ epg.py 解析/频道映射
        ▼
预约计划 records.json ──→ RecordManager（调度线程，1s tick）
                              │ 启动/停止/恢复/配额
组播源 ──加组收流──→ Recorder（剥 RTP → 写 .ts，IGMP 续期，断流重加组）
                              │
                        录像目录 record_dir/（ts 文件 + recordings.json 索引）
                              │
        proxy 常驻服务（一个进程搞定）:
          /udp/<g>:<p>      直播转发（现有）
          /vod/<id>         录像点播（Range，多分段虚拟拼接）
          /recordings.m3u   录像播放列表（VOD）
          /recordings.json  录像索引
          /status           状态（扩展录制信息）
                              │
              VLC / Kodi / PotPlayer / TiviMate（局域网）
```

NAS 上只需一条命令：`proxy --channels verified.json --record-dir /volume1/iptv/rec`，
直播转发 + 预约调度 + 录像点播全部在这个前台长驻进程里（符合现有 CLI 长任务约定：放后台、解析 stderr JSONL）。

## 4. record.py 核心设计

### 4.1 Recorder（单频道录制器）

```python
class Recorder:
    def __init__(self, channel, iface_ip, out_path,
                 stop_evt=None, progress_cb=None, sock_factory=None):
        """channel: {name, group, port, ...}（与 verify/m3u 同一套频道 dict）
        sock_factory: 测试注入用，缺省创建真实组播 socket"""
    def run(self): ...   # 阻塞录制循环，在独立线程中调用
    def stop(self): ...  # 置 stop_evt，优雅收尾
    stats: dict          # bytes, pkts, duration, gaps, parts, error
```

录制循环要点：
1. **加组**：与 `verify.verify_channel` 完全相同的 socket 参数
   （`SO_REUSEADDR` → `bind(('', port))` → `IP_ADD_MEMBERSHIP` → `IP_MULTICAST_IF`），
   保证「verify 能收的就能录」，169.254.x 搭线地址同样可用。
2. **写盘**：`tsutil.strip_rtp(data)` 剥 RTP 头后追加写 `.ts`（兼容裸 UDP-TS 与 RTP 封装）。
   缓冲写（64KB 级别），每 5s flush；**文件首包尽量等到 PAT/PMT**（用 `TSAnalyzer` 轻量判断，
   最多等 2s，等不到也照写——播放器可自行恢复同步）。
3. **IGMP 续期**：直接复用 `proxy._refresh_loop`（60s 周期补发 report；raw socket 需管理员，
   不可用时自动回退 drop/re-add——**因此录像不需要管理员**，与 proxy 现状一致）。
4. **断流自愈**：`recvfrom` 超时 6s → 计数并 drop/re-add 重加组，继续写同一文件；
   每次断流记 `gaps += 1` 并通过 `progress_cb` 上报（CLI 走 stderr JSONL `record_gap`）。
   连续失败不放弃，直到 stop 或计划结束——录到一半断流几分钟，恢复后继续录仍有价值。
5. **分段**：单文件超过 4 GiB 或 2 小时 → 切 `_p2.ts`、`_p3.ts`…（兼容 FAT32/老 NAS，
   避免超大文件）。分段对播放器透明（§5.3 虚拟拼接）。
6. **磁盘保护**：启动前与录制中周期检查 `shutil.disk_usage`，剩余空间低于
   `max(2 GiB, 10 分钟 × 实测码率)` 时优雅停止并标记 `error='disk_full'`。
   码率用前 10 秒字节数估算。
7. **收尾**：flush + close，产出 `stats`；任何异常都要保证文件句柄关闭、索引落盘。

### 4.2 RecordManager（调度与持久化）

```python
class RecordManager:
    def __init__(self, record_dir, iface_ip, channels_cb=None,
                 quota_gb=20, pad_before=60, pad_after=120,
                 max_concurrent=2, missed_policy='skip', now_fn=None):
        """now_fn: 测试注入假时钟；channels_cb 与 ProxyServer 同源"""
    def start(self): ...          # 起调度线程（1s tick）+ 重启恢复
    def stop(self): ...           # 停调度；进行中的录制优雅收尾
    def add_schedule(self, ch, start, end, source='manual', epg_title=''): ...
    def cancel(self, sid): ...
    def record_now(self, ch, seconds): ...   # 即时录（等价于 start=now 的临时计划）
    def list_schedules(self): ...
    def list_recordings(self): ...
    def delete_recording(self, rid): ...
    def status(self): ...         # 活跃录制 + 计划摘要，供 /status 与 GUI
```

调度规则：
- `now >= start - pad_before` 且并发未满 → 启动 Recorder（线程）；
  并发上限默认 **2**（与 verify 默认并发一致：光猫可能限速加组，高并发易假失败）。
- `now >= end + pad_after` → 停止、收尾、写索引、触发配额清理。
- 同一频道同一时段去重；计划冲突（同频道重叠）拒绝并报错。
- **重启恢复**（`start()` 时扫描 `records.json`）：
  - `status=recording`：`now < end+pad` → 续录剩余时段（新分段文件，追加进同一录像索引）；
    否则按已完成收尾（标记 partial）。
  - `status=pending` 且时段已过：`missed_policy='skip'` → 标 `missed`；
    `'remainder'` → 若 `now < end` 立即开录剩余部分。
- 所有状态变更**原子落盘**（tmp + `os.replace`，与 `cli._write_json` 同法）。

### 4.3 目录与文件布局

`record_dir` 是唯一需要 NAS 挂载的目录，状态与数据全部在内（便于备份/迁移）：

```
record_dir/
  records.json          # 预约计划（含历史状态）
  recordings.json       # 录像索引（进行中 + 已完成）
  epg.xml.gz            # EPG 原始缓存（用户主动更新产生）
  epg.json              # 解析后的轻量缓存（仅映射成功的频道、未来 7 天节目）
  ts/
    <rid>.ts            # 录像文件（rid 见下）
    <rid>_p2.ts ...     # 分段
```

- 文件主名 `rid = r<YYYYmmdd_HHMMSS>_<safe_name>`，`safe_name` 由
  `channeldb.normalize_name` + 文件系统非法字符清洗（`\\/:*?"<>|` → `_`，截断 40 字符）。
  例：`r20261123_193000_CCTV5.ts`。可读、可排序、不依赖索引也能认。
- 索引缺失/损坏时可从 `ts/` 文件名重建基础索引（降级可用）。

### 4.4 数据结构

`records.json`（数组，每条计划）：

```json
{
  "id": "a1b2c3d4",
  "channel": {"name": "CCTV5", "group": "233.50.201.118", "port": 5140},
  "start": "2026-11-23T19:30:00", "end": "2026-11-23T21:30:00",
  "source": "epg", "epg_title": "英超：阿森纳 vs 利物浦",
  "status": "pending|recording|done|missed|canceled|error",
  "rid": "r20261123_192900_CCTV5",
  "error": "", "created": "2026-11-22T22:00:00"
}
```

`recordings.json`（数组，每条录像）：

```json
{
  "id": "r20261123_192900_CCTV5",
  "name": "CCTV5", "epg_title": "英超：阿森纳 vs 利物浦",
  "group": "233.50.201.118", "port": 5140,
  "start": "2026-11-23T19:29:00", "end": "2026-11-23T21:32:00",
  "duration": 7380, "bytes": 3221225472,
  "parts": [{"file": "ts/r20261123_192900_CCTV5.ts", "bytes": 2147483648},
            {"file": "ts/r20261123_192900_CCTV5_p2.ts", "bytes": 1073741824}],
  "status": "recording|done|partial|error",
  "gaps": 0, "error": ""
}
```

时间一律**本地时间 ISO 格式**（无时区后缀，与用户直觉一致；国内无 DST 问题）。
`duration/bytes` 录制中为实时累计值，收尾时定格。

### 4.5 配置项（GUI cfg 与 CLI 缺省值共用）

`DEFAULT_CFG` 新增（`src/main.py`，注意 `_load_cfg` 只认 DEFAULT_CFG 里已有的键）：

| 键 | 缺省 | 说明 |

## 5. proxy.py 扩展（点播服务）

`ProxyServer.__init__` 增加可选参数 `record_mgr=None`（向后兼容，现有调用不受影响）。
`record_mgr` 非空时启用以下端点：

### 5.1 `/vod/<rid>`（核心）

- **只认索引里的 rid**（白名单），绝不接受任意路径 → 天然防路径穿越；未知 rid → 404。
- 支持 `Range: bytes=a-b` / `bytes=a-` / `bytes=-n`（后缀范围）：
  - 命中 → `206 Partial Content` + `Content-Range: bytes a-b/total`；
  - 不可满足 → `416`；无 Range → `200` 全量。
  - 响应头：`Accept-Ranges: bytes`、`Content-Type: video/MP2T`、`Content-Length` 精确。
- **多分段虚拟拼接**：按索引 `parts` 的字节偏移把请求范围映射到各分段文件，
  跨段请求依次读取拼接输出——纯 Python 实现，不复制文件，播放器看到的是连续单文件。
- 支持 `HEAD`（播放器探测时长/可拖动性用）。
- 录制中的文件也可播（`status=recording`）：`total` 取当前累计字节，实现「边录边看」。
- 并发读多个客户端互不影响（ThreadingHTTPServer 现有模型）。

### 5.2 `/recordings.json` 与 `/status`

- `/recordings.json`：索引原样输出（含进行中），供脚本/GUI 远程管理。
- `/status`：现有 JSON 增加 `recordings` 字段（活跃录制 rid/name/bytes/duration/gaps +
  未来 24h 计划数），保持现有字段不变。

### 5.3 `/recordings.m3u`

```
#EXTM3U
#EXTINF:7380 tvg-name="CCTV5" group-title="录像",CCTV5 英超：阿森纳 vs 利物浦 (11-23 19:29)
http://<lan_ip>:<port>/vod/r20261123_192900_CCTV5
```

- `#EXTINF` 时长用真实秒数（VOD 语义，区别于直播的 -1）；
- 标题 = 频道名 + EPG 节目名（有则加）+ 开播时间；`group-title="录像"`；
- 只列 `done/partial/recording`，按开始时间倒序；
- 生成逻辑放 `m3u.py` 新函数 `write_recordings_m3u(...)`（与现有 M3U 代码同处，GUI/CLI/proxy 共用）。
- 直播列表 `/playlist.m3u` **不混入录像**（直播与点播分开，播放器行为可预期）。

## 6. epg.py 设计（P2）

### 6.1 数据源（公共 XMLTV，仅用户主动触发）

内置候选（逐个尝试，任一成功即用；`--url`/`epg_url` 自定义优先）：
- `https://epg.pw/xmltv/epg_CN.xml.gz`（2026-11 实测可用；旧 `/api/epg.xml?lang=zh` 已 404）
- `https://epg.pw/xmltv/epg_CN.xml`
- `http://epg.51zmt.top:8000/e.xml`、`https://epg.112114.xyz/pp.xml`（部分网络可达，兜底）

下载走 `urllib`（标准库），支持 gzip；进度回调模式与 `refupdate.fetch_online` 一致
（CLI stderr JSONL `epg_update_progress`）。**默认不自动联网**；`epg_update_on_start`
是用户显式 opt-in 的例外，帮助文本需注明。

### 6.2 解析与缓存

- `xml.etree.ElementTree.iterparse` 流式解析（XMLTV 全量可达数十 MB，防内存爆）；
- 原始文件存 `epg.xml.gz`；解析产物 `epg.json` **只保留映射成功频道、未来 7 天**的节目
  （title/start/stop/desc），控制体积；
- 节目时间格式 `YYYYMMDDHHMMSS +0800` → 本地 datetime。

### 6.3 频道映射

- 键：XMLTV `channel id` + `display-name`；值侧用 `channeldb.normalize_name` 归一；
- 内置别名规则：`CCTV-1/CCTV1/CCTV-1综合 → CCTV1`、`XX卫视高清 → XX卫视`、
  全角/空格/「频道」后缀清洗；有 `tvg_id` 的导入频道优先精确匹配；
- `epg map` 输出映射报告（成功/失败清单），失败频道仍可按时间段手动预约；
- 映射表允许用户自定义别名（`epg.json` 内 `aliases` 段，GUI 可编辑，P2 后期）。

### 6.4 预约联动

`record add --name CCTV5 --title "英超"`（可加 `--date`）→ 在 EPG 缓存中查该频道
未来匹配的节目 → 取其 start/stop（加 pad）建计划。查不到 → 报错并提示改用
`--start/--end` 手动模式或先 `epg update`。

## 7. CLI 设计（协议完全沿用现有约定）

stdout 单个 JSON（`result()` 包装 ok/tool/version/command）、stderr JSONL（`log()`）、
退出码 0/1/2/3、`--out FILE`、频道来源接受 `read_channels()` 全部格式。**不需要管理员。**

### 7.1 子命令总览

| 命令 | 作用 | 阶段 |
|---|---|---|
| `record start` | 前台即时录制（Ctrl+C 优雅停止并收尾） | P1 |
| `record add` | 添加预约（需常驻服务在跑，否则提示） | P2 |
| `record list` | 计划 + 活跃录制 + 已完成录像 | P1( files )/P2(全量) |
| `record cancel --id SID` | 取消预约 | P2 |
| `record delete --id RID` | 删除录像文件与索引 | P1 |
| `epg update [--url URL]` | 主动更新 EPG 缓存 | P2 |
| `epg show --name X [--date D]` | 查某频道节目单 | P2 |
| `epg map` | 频道↔EPG 映射报告 | P2 |
| `proxy --record-dir DIR` | 常驻：转发 + 调度 + 点播 | P1(点播/即时录管理)/P2(调度) |

### 7.2 关键参数与示例

```bash
# 即时录 90 分钟（频道来源三选一，与 verify 一致）
WushuangIPTV-CLI.exe record start --channels verified.json --name CCTV5 --minutes 90 \
    --record-dir D:\rec --iface 192.168.1.10 --out rec_result.json
```

### 7.4 即时录与常驻服务的关系

- `record start` 是**独立前台进程**，不依赖 proxy 在跑（录完文件直接可用）；
- 若同目录已有常驻 RecordManager，`record start` 通过索引文件协调并发上限
  （启动前读 `recordings.json` 统计 recording 数，超限报错退出，避免双进程超录）；
- 预约调度**只存在于常驻服务**（proxy --record-dir / GUI 录像服务），
  `record add` 写 `records.json` 后由常驻进程 tick 拾取（文件 mtime 轮询，无需 IPC）。

## 9. 可靠性与边界情况

| 场景 | 处理 |
|---|---|
| 光猫无 IGMP 查询器，加组老化断流 | `_refresh_loop` 60s 续期（现有实测方案）；非管理员走 drop/re-add 回退 |
| 录制中流中断（换台/网络抖动） | 6s 超时 → 重加组续录同一文件，gaps 计数上报；不放弃直到计划结束 |
| 进程/设备重启 | records.json 恢复：recording 续录剩余、pending 过期按 missed_policy |
| 磁盘将满 | 启动前预检 + 录制中周期检查，优雅停止标 error，不写坏文件 |
| 配额超限 | 收尾后按结束时间 LRU 删最旧已完成录像；**绝不删进行中/待录文件** |
| 双进程同目录（CLI 即时录 + 常驻） | 启动前读索引统计并发，超限退出码 1 并提示 |
| 计划时间冲突/重名频道 | add 时校验拒绝，报错列候选 |
| 索引损坏 | 从 ts/ 文件名重建基础索引（降级：无 EPG 标题/精确时长） |
| 文件系统非法字符/超长频道名 | safe_name 清洗 + 截断 |
| 时钟偏差 | pad_before/after 默认 60/120s 吸收；帮助文本建议 NAS 开 NTP |
| 录制中删除文件 | delete 拒绝 recording 状态条目（先停止再删） |

## 10. 播放兼容性

- **TS over HTTP + Range**：VLC / Kodi / PotPlayer / IINA / TiviMate(VOD) 拖动良好
  （按码率估算字节偏移，TS 无索引也可 seek，精度秒级）；
- DIYP/影视仓等直播向 App 对 VOD 列表支持不一 → 录像列表独立成 `/recordings.m3u`，
  文档注明推荐播放器；P3 提供 HLS 切片兜底；
- 不做 MP4：零依赖约束下 remux 成本/风险高，TS 全平台可播，收益不成比例；
- 4K 高码率（50Mbps+）：每小时 ~22GB，配额默认 20GB 会很快触顶——
  文档提示 4K 用户调大配额或缩短预约。

## 11. 安全与隐私

- 沿用红线：**仅限局域网，禁止映射公网**；`/vod/` 白名单 rid，无路径穿越面；
- 录像功能**不接触任何机顶盒账号/鉴权信息**（与 capture 的 stb 字段完全无关）；
- EPG 更新是唯一新增联网点：默认仅用户显式触发（同 `refdb update`），
  `epg_update_on_start` 为显式 opt-in；不上传任何数据；
- 录像文件为公开播出的电视内容，仅供个人观看（帮助文本注明版权边界）；
- `wan/` 公网鉴权转发本期不改动；录像若未来要远程看，走 wan 代理加 token 的既有安全模型，
  另立设计，不在本期范围。
